# Формат обмена между планировщиком и применяющим скриптом (черновик v1)

Excel остаётся отчётом для людей. Между программами нужен машинный формат, потому что его читает не человек,
а применяющий скрипт (`ozon_skleyki.py` и `wb_skleyki.py`, которые будут переписаны).

## Принципы

1. **Планировщик и применяющий скрипт не знают друг о друге.** Они знают только контракт (план). Планировщик не ходит на площадку
   за записью, применяющий скрипт не придумывает группы.
2. **План декларативный:** «какие артикулы должны быть вместе», а не «какие вызовы API сделать». Список вызовов
   (операции) применяющий скрипт строит сам, сравнивая план с живым состоянием площадки.
3. **Идемпотентность:** повторное применение того же плана ничего не меняет, прерванное применение можно продолжить.
4. **Всё проверяемо и обратимо:** у каждой операции записано «было → стало», по ним строится откат.
5. **Безопасность в два слоя:** планировщик гарантирует правила (бренд, тип, размеры), применяющий скрипт перед записью
   проверяет их ещё раз по живым карточкам и отказывается применять группу с нарушением.

## Компоненты

```
данные (БД) ─► планировщик ─► ПЛАН (run) ─► согласование ─► применяющий скрипт ─► площадка
                  │                 │                              │
              состояние        отчёт Excel                  операции + результат
              (вчерашние        для людей                  (в той же БД, для отката)
               группы)
```

Три пакета в одном репозитории, зависимости только в одну сторону: `contract` ← `planner`, `contract` ← `applier`.

## План (JSON, версия 1)

Один запуск = один план. Пример реальной группы (Timeless, пододеяльники), сокращён:

```json
{
  "schema_version": 1,
  "run": {
    "run_id": "2026-10-09-ozon",
    "platform": "ozon",
    "created_at": "2026-10-09T06:00:00Z",
    "engine_version": "git:<хэш>",
    "profile": {"name": "ozon", "hash": "<хэш настроек>"},
    "inputs": {"stock_snapshot": "2026-10-09", "orders_window_days": 28, "rolls_snapshot": "2026-10-09"},
    "mode": "shadow"
  },
  "groups": [
    {
      "group_id": "g_b62935cf",
      "key": "timeless|Timeless|Пододеяльник|Обычные#1",
      "account": "timeless",
      "brand": "Timeless",
      "type": "Пододеяльник",
      "branch": "Обычные",
      "kind": "glue",
      "n_designs": 18,
      "n_skus": 35,
      "target": {"ozon": {"model_name": "g_b62935cf"}},
      "designs": [
        {"design": "125", "feature": "Обычные",
         "members": [
           {"offer_id": "125/5-0-0/1", "product_id": null, "stock": 5, "orders_28d": 11},
           {"offer_id": "125/6-0-0/1", "product_id": null, "stock": 7, "orders_28d": 15}]}
      ],
      "reasons": ["бренд и тип — жёстко", "признак «Обычные»", "в ветке 18 дизайнов, делить не нужно"]
    }
  ],
  "unglued": [{"offer_id": "PT6361/130-147/чехол", "reason": "one_sku_in_type"}],
  "checks": {"hard_violations": [], "warnings": ["brand_mismatch: 11 карточек PT6421"]},
  "decisions": [{"node": "timeless|Timeless|Наволочка", "level": "признак", "name": "Рюши", "n": 18, "result": "отделён"}]
}
```

Что важно в формате:
- **`group_id`** стабильный и непрозрачный (хэш от человекочитаемого `key`). На Озоне он же значение «Название модели»,
  на WB используется как внешний ключ. Один и тот же состав и ветка дают один и тот же id изо дня в день.
- **`kind`:** `glue`, `small_glue` (2–5 дизайнов), `single_design` (SKU одного дизайна вместе), `unglued`.
- **`target`** специфичен для площадки: Озон `{model_name}`, WB `{imt_id | "new"}`. Остальная часть общая.
- **`members`** содержат идентификаторы площадки (`product_id`, `sku` для Озона, `nm_id` для WB). Планировщик берёт их из
  `product_cards`, применяющему скрипту не нужно ничего искать по артикулу.
- **`reasons`** и **`decisions`** объясняют результат и нужны для отчёта «почему так» и для состояния гистерезиса.
- **`checks`** содержит нарушения жёстких правил (если есть, план не может быть применён) и предупреждения.

## Хранение

Источник истины: схема `gluing` в Postgres (то же сервер, отдельная схема, не таблицы `db_sync`). Тот же план можно
выгрузить в JSON (для тестов, архива и ручной проверки). Excel строится из плана и ничего не хранит.

```sql
gluing.run(run_id pk, platform, created_at, engine_version, profile_hash, inputs jsonb,
           mode, status, approved_by, approved_at)            -- draft/approved/applying/applied/partial/failed/reverted
gluing.group(run_id, group_id, key, account, brand, type, branch, kind, n_designs, n_skus, target jsonb, reasons jsonb)
gluing.member(run_id, group_id, offer_id, platform_ids jsonb, design, feature, stock, orders_28d)
gluing.decision(run_id, node, level, name, n, result)          -- и гистерезис, и «почему»
gluing.live_state(run_id, offer_id, model_name, imt_id, read_at)   -- что было на площадке до применения
gluing.op(run_id, op_id, offer_id, op_type, from_value, to_value, status, error, applied_at)  -- журнал применения
```

Вчерашнее состояние для «липкого» назначения и гистерезиса планировщик берёт из `gluing.decision` и `gluing.member`
предыдущего успешного запуска, а не из файлов. Первый запуск стартует от живого состояния площадки (`live_state`).

## Жизненный цикл запуска

`draft` (план построен, проверки пройдены) → `approved` (согласован человеком или правилом) → `applying` →
`applied` | `partial` | `failed` → при необходимости `reverted`.

Режимы: `shadow` (только план и отчёт, на площадку ничего), `manual` (применяется после «да» человека),
`auto` (применяется сам, но только если проверки чистые, число перемещений в пределах лимита, нет предупреждений
выше порога; иначе останавливается и сообщает).

## Применяющий скрипт (как он должен работать)

1. Взять согласованный план. Режим по умолчанию `dry-run`: показать операции, ничего не менять.
2. Прочитать живое состояние карточек плана (Озон: «Название модели» и атрибуты; WB: imtID) и записать в `live_state`.
3. Построить операции по разнице «живое состояние → план» (только изменения).
4. Предварительные проверки по живым данным: тип и бренд, размер группы, «близнецы» вариативных характеристик (как сейчас),
   карточка существует. Группу с нарушением не применять, а вынести в отчёт.
5. Применять пакетами с учётом лимитов и повторов. Каждую операцию записывать в `op` со статусом.
6. Спустя паузу перечитать состояние и сверить (Озон собирает модели от минут до суток, WB выводит чужих асинхронно),
   незавершённое доклеить, итог записать в `run`.
7. Откат: план «обратной разницы» строится из `from_value`.

Платформенные детали остаются внутри применяющего скрипта и не попадают в контракт: Озон меняет атрибут 9048 пакетами по 100,
WB переносит карточки через `moveNm`, учитывает лимит 30 и вывод чужих.

## Валидация и версии

Один пакет `contract` с моделями (pydantic) и JSON Schema; его импортируют и планировщик, и применяющий скрипт, поэтому расхождение
форматов ловится при записи плана. Поле `schema_version`: новые необязательные поля добавляются без смены версии,
несовместимые изменения повышают версию, применяющий скрипт отказывается читать незнакомую.

## Что уже есть и чего не хватает

Есть: группы, состав, признаки, причины, решения, состояние гистерезиса (в JSON), метрики.
Не хватает: стабильные `group_id`, идентификаторы площадки у карточек (`product_id`, `nm_id`), хранение в БД,
чтение из БД, статусы запуска, обратная разница для отката.

## Решения (обсуждение 09.10)

1. Схема `gluing` лежит в той же базе `marketplace_sync`, что и данные `marketplace_db_sync`, но это отдельная схема со своей ролью.
   Планировщик читает таблицы `public` только на чтение и пишет только в `gluing`.
2. Согласование делается через интерфейс (см. ниже), кнопка «Согласовать» запускает применение на сервере.
3. Применяющий скрипт пишется в этом же репозитории отдельным пакетом `applier`; пакет `contract` общий.
4. Номера групп для проверки (OZ-001...) показываются в Excel и интерфейсе и считаются при формировании отчёта.
   Внутренний `group_id` стабильный (см. «Идентификаторы»).

## Интерфейс проверки и согласования

Коллега открывает веб-страницу с сервера (из любого офиса; доступ через Tailscale, как к серверу), видит группы текущего плана,
перетаскивает дизайны между группами и нажимает «Согласовать».

- **Что перетаскивают:** дизайны целиком (на Озоне дизайн не делится). Бренд и тип сервер проверяет сам: перенос между разными
  типами или брендами запрещён, размер группы 6–18 и малые группы показываются предупреждением, а не запретом.
- **Живые показатели** при правке: размеры групп, хит и неликвид, чистота, сколько дизайнов переехало относительно живого состояния.
- **Согласование:** перед кнопкой виден предварительный просмотр (сколько операций, сколько групп затронуто, что изменится
  относительно Озона). Кнопка меняет статус плана на `approved`, фоновый процесс подхватывает и применяет. На странице виден ход
  применения и итог, есть «Остановить» и «Откатить». Если перемещений больше лимита, нужно второе подтверждение.
- **Роли:** просмотр, правка, согласование. Каждое действие пишется в `audit` (кто, когда, что).
- **Ключи площадок** остаются только на сервере (в окружении, как у `db_sync`); интерфейс их не видит и не хранит.

## Ручные правки не должны пропадать

Если коллега перенёс дизайн, завтра планировщик не имеет права вернуть его обратно. Поэтому каждая ручная правка сохраняется как
закрепление (`pin`): «дизайн X живёт в группе K». Правила:
- Планировщик уважает закрепление, пока оно не нарушает жёсткое правило (бренд, тип). Если нарушает, снимает с предупреждением.
- У закрепления есть автор, причина и срок (можно бессрочно); в интерфейсе их видно и можно снять.
- Начальное состояние следующего дня берётся из живого состояния площадки (то, что реально применено вместе с правками),
  а не из вчерашнего плана.
- Только один запуск в статусе `draft` на площадку; новый плановый запуск заменяет несогласованный (`expired`),
  а правки из него сохранены закреплениями.

## Идентификаторы

- Группа наследует прежнее «Название модели», если её состав на 50% и больше совпадает с живой моделью на Озоне
  (и имя ещё не занято). Так при переходе на новый формат не создаются лишние операции: ни один артикул не получает новое имя без причины.
- Новая группа получает новый короткий id (`g_<хэш>`); он остаётся за ней, пока группа существует.
- Человекочитаемый номер (OZ-001...) нужен только для показа в Excel и интерфейсе и не хранится как идентификатор.

## Этапы

1. **Основа планировщика (серверная часть).** Схема `gluing` и роль (черновик в `migrations/001_gluing_schema.sql`, не применён),
   чтение данных из БД (карточки, остатки, заказы, рулоны), запись плана, наследование id, ежедневный запуск в теневом режиме
   после синка (Планировщик заданий), отчёт Excel из плана.
2. **Применяющий скрипт для Озона.** Прогон без изменений (diff), проверки, применение, сверка, откат; тесты на «фальшивой»
   площадке; сначала запуск вручную из командной строки.
3. **Интерфейс.** Сначала только просмотр, затем правки с закреплениями, затем «Согласовать», ход применения и откат.
4. **WB** в той же схеме (цель — `imt_id`, `moveNm`, лимит 30), затем автоматический режим.

Этапы 1 и 2 дают ценность и без интерфейса: можно смотреть ежедневные планы и применять вручную по команде.
